# F0 — Baseline, inventário, proteção dos dados e preparação

Status: VERIFICADA

## Objetivo
Validar o estado real do repositório, conferir os requisitos da etapa F0 e completar a preparação necessária para o restante do projeto sem avançar para F1.

## Requisitos aplicáveis
- RF-001: preservar a biblioteca existente e evoluir sem destruir IDs, proprietário, conteúdo, seções, anexos e metadados legados.
- RNF-003: proteção dos dados, com validação de proprietário e URLs/arquivos seguros.
- RNF-009: manutenibilidade e validação.
- Requisitos de qualidade associados a preparação de ambiente, proteção de segredos e verificações de baseline.

## Estado real do código
- O repositório já contém uma implementação funcional do backend em NestJS e do frontend em Next.js.
- A pasta `docs/notion` contém a especificação e os materiais de engenharia reversa; não havia um registro de execução em `docs/notion/execucao` antes desta etapa.
- O arquivo `.gitignore` já protege segredos e artefatos locais, incluindo `.env`, `.env.*`, arquivos `.zip` e diretórios de build.
- O frontend tinha um problema real de preparação: `NEXT_PUBLIC_API_URL=http://localhost:3000` e `NEXT_PUBLIC_STORAGE_URL=http://localhost:9000/biblioteca-estudos` eram carregados em build de produção, acionando a proteção de loopback do `next.config.ts`.

## Decisões e ajustes
1. Mantivemos a proteção padrão: em produção, URLs com host de loopback continuam sendo rejeitadas para evitar exposição/acoplamento acidental.
2. Adicionamos um override explícito para smoke tests locais: `ALLOW_LOOPBACK_IN_BUILD=true`.
3. Atualizamos a documentação do frontend para deixar esse comportamento explícito e não ambíguo.

## Observações de validação
- Sem o override explícito, o build de produção continua bloqueado quando `NEXT_PUBLIC_API_URL` aponta para localhost; esse comportamento é desejado como proteção e não deve ser removido por padrão.
- O override foi usado somente para verificação local controlada, não para publicação nem para produção real.
